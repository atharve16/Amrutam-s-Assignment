# Database decisions — Milestone 2

This document records design choices made where the assignment is silent. They are implementation decisions, not newly invented business requirements.

## Assumptions and scope

- A user signs in with a password and at least one of a normalized email address or an E.164 phone number. The assignment requires authentication but does not choose an identifier.
- A user has one server-controlled role: `patient`, `doctor`, or `admin`. Supporting multiple simultaneous roles would require a role-mapping table and is deferred until a concrete need exists.
- Availability is modeled as discrete, single-consultation intervals. Arbitrary appointment durations assembled from smaller blocks would make overlap, pricing, and locking more complex without an assignment requirement.
- A consultation can have several cancelled booking attempts for the same slot, but at most one non-cancelled consultation. Completed and no-show consultations continue to reserve their historical slot; only cancellation releases it.
- Payments are attempts, so a consultation can have many payment rows. This supports retries and future partial/refund policies without claiming a real gateway exists.
- A consultation can have versioned prescriptions. Medication lines are relational rows rather than an opaque JSON array.
- Retention periods below are operational starting assumptions and require legal/compliance approval before production.

## IDs and timestamps

Domain and integration-facing records use UUID primary keys generated by PostgreSQL with `gen_random_uuid()`. This gives one consistent strategy across application replicas and allows IDs to be created inside the same transaction as their records. `audit_logs` is the exception: an identity `bigint` is smaller and naturally ordered for a high-volume append-only stream. It is not exposed as a security boundary.

All instants use `timestamptz` and are interpreted as UTC instants. APIs must accept ISO 8601 values with an explicit offset and return UTC. A profile may hold an IANA time-zone name for presentation, but local clock values are never stored for bookings. Dates and timestamps do not themselves authorize a lifecycle transition.

## Status representation

Statuses are `text` columns protected by named check constraints. PostgreSQL enums provide compact values but make removals and some deployments harder. Text checks are visible, transactional, and extended through a normal migration. Application code must still enforce transition graphs; a check constraint only validates the resulting state.

| Record              | Allowed states                                                                 |
| ------------------- | ------------------------------------------------------------------------------ |
| User                | `pending`, `active`, `suspended`, `deactivated`                                |
| Doctor verification | `pending`, `verified`, `rejected`, `suspended`                                 |
| Availability        | `open`, `blocked`, `cancelled`                                                 |
| Consultation        | `scheduled`, `in_progress`, `completed`, `cancelled`, `no_show`                |
| Prescription        | `draft`, `issued`, `void`                                                      |
| Payment             | `created`, `pending`, `succeeded`, `failed`, `cancelled`, `refunded`           |
| Session             | `active`, `rotated`, `revoked`, `compromised` (`expires_at` determines expiry) |
| MFA factor          | `pending`, `active`, `revoked`                                                 |
| Idempotency         | `processing`, `completed`, `failed`                                            |
| Outbox              | `pending`, `processing`, `processed`, `dead_letter`                            |

## Identity and contact normalization

`users.email` contains the canonical lower-case, trimmed form; a check constraint enforces that representation and a partial unique index enforces case-insensitive uniqueness because all stored values are canonical. The registration DTO validates and normalizes email before insertion. `phone_e164` remains schema-supported but is not exposed by the MVP registration API.

Password hashes are Argon2id encoded strings, never plaintext. Refresh tokens are represented only by cryptographic hashes in `sessions`. TOTP secrets live in `mfa_factors.secret_ciphertext`, encrypted by an application-managed versioned key; they cannot be hashed because verification needs the original secret. No key is stored in PostgreSQL.

## Slot and booking correctness

Availability ranges use half-open `[start, end)` semantics. Adjacent slots are valid; overlapping `open` or `blocked` slots for one doctor are rejected by a GiST exclusion constraint over `tstzrange`. Cancelled slots no longer conflict, so corrected schedules can be created while the cancelled row remains historical.

Slot status describes whether the doctor offers the interval. It does not duplicate booking state. Search queries select `open` slots and exclude those with a non-cancelled consultation. A slot with a consultation must not be blocked or cancelled until the consultation is cancelled; this cross-record transition is enforced by the future service transaction and audit event.

`consultations` snapshots the scheduled start/end for efficient history queries and historical integrity. A composite foreign key to `(slot_id, doctor_id, starts_at, ends_at)` ensures the snapshot and doctor exactly match the referenced slot. A partial unique index on `slot_id WHERE status <> 'cancelled'` is the final double-booking guard.

Future booking transaction:

1. Begin a database transaction and establish the idempotency record.
2. Read the slot and validate doctor, time, and `open` status. A row lock may improve the error path but is not the correctness mechanism.
3. Insert a `scheduled` consultation. Concurrent inserts for the same slot race on the partial unique index; exactly one can commit.
4. Insert the audit row and outbox event in the same transaction.
5. Mark the idempotency record complete and commit. Map unique violation `23505` for the active-slot index to HTTP `409 Conflict`.

Cancellation changes the active consultation to `cancelled`, sets `cancelled_at`, and writes audit/outbox records atomically. The partial-index entry disappears, so a new consultation may reserve the slot while the cancelled row remains. Completed and no-show rows cannot be displaced. Service transition rules prohibit reopening a cancelled consultation.

## Idempotency

Authenticated requests are uniquely scoped by `(actor_id, operation, idempotency_key)`. Anonymous operations use a 32-byte hash of a stable, privacy-safe scope instead of an IP address or raw identifier. Separate partial unique indexes avoid PostgreSQL's ordinary `NULL`-distinct behavior.

The stored SHA-256 request fingerprint covers the canonical method, operation, and validated payload. For the first request, the record and business change are created in one transaction. A concurrent identical key loses the unique race, reads the winner, and either returns its completed safe response or reports processing. A different fingerprint is a conflict. A retry after timeout receives the recorded response/resource. Failure before commit rolls back the record and business change; failure committed as a known response records `failed`; a crash after commit still leaves `completed`. `response_body` must contain only the minimum replay-safe representation and no tokens or sensitive clinical content.

## Sessions and MFA

Each refresh rotation creates a new `sessions` row in the same token family and marks the previous row `rotated`. A composite self foreign key enforces the same user/family lineage. A partial unique index permits one active row per family. `parent_session_id` is unique, preventing two successful children from one refresh token. Reuse of a rotated token causes the implemented service to mark the active family descendant compromised. Expiry is derived from `expires_at`; cleanup need not mutate every row at the moment it expires.

One pending or active TOTP factor is allowed per user. `last_used_time_step` supports replay rejection. MFA enrollment, encryption, recovery, and verification remain unimplemented and are not claimed by the MVP.

## Prescriptions and payments

The composite prescription foreign key `(consultation_id, doctor_id)` references the consultation's assigned doctor, preventing a different doctor from becoming the recorded author. The implemented service additionally requires the authenticated assigned doctor and a completed consultation.

A consultation can have multiple prescription versions but only one currently `issued` version. Voiding an issued version and issuing its successor is one transaction. Medication name, dosage, frequency, duration, and optional instructions are separate `prescription_items` rows.

Payment amounts use exact `numeric(12,2)` and uppercase ISO-style three-letter currency text. Provider and external reference are optional; when both exist their pair is unique. Provider callbacks and success status are never trusted from clients. The schema permits multiple attempts and does not assert that a gateway is integrated.

## Deletion policy

Accounts are deactivated rather than routinely deleted. Historical clinical and financial foreign keys use `RESTRICT`. Owned security/profile records (`profiles`, `sessions`, and `mfa_factors`) use `CASCADE` only if an exceptional hard deletion is able to pass every historical restriction. Verification and cancellation actor references use `SET NULL`, preserving the event without preventing an approved identity purge. Audit actors use `SET NULL`; generic audit/outbox resource IDs are intentionally not foreign keys because they span resource types and must outlive them.

`prescription_items` use `RESTRICT`, so a prescription with medication lines cannot disappear through a cascade. Database owners can still bypass normal application policy; production roles and audited maintenance procedures remain necessary.

## Audit and outbox

Audit metadata is a JSON object for sparse, non-sensitive context only. A trigger rejects updates and deletes, except for the exact actor-nulling update needed by the `ON DELETE SET NULL` foreign key during an approved identity purge. Production grants must still deny general update permission, because a caller with update access could otherwise invoke that anonymization path directly. A database owner can disable or bypass the trigger, so this is tamper resistance rather than cryptographic immutability. Access should be limited to a dedicated insert path and restricted administrative readers.

An outbox event is inserted by the same transaction as its business aggregate. A future worker claims pending rows with `FOR UPDATE SKIP LOCKED`, changes them to `processing`, and commits the claim. Success records `processed`; retryable failure returns to `pending` with incremented attempts and a future `next_attempt_at`; exhaustion becomes `dead_letter`. Partial indexes support claiming and stale-lock recovery. Payloads contain identifiers and minimal event data, not full prescriptions or credentials.

## Index and partition decisions

Indexes match documented reads: normalized contacts, verified-doctor search, doctor/time availability, patient/doctor consultation history, consultation prescriptions/payments, active sessions, idempotency scope/expiry, audit actor/resource/time, and pending/stale outbox work. Every index adds write amplification; low-selectivity status columns are indexed only as part of a concrete query or partial predicate.

The assignment target of 100,000 consultations/day implies roughly 36.5 million/year before retention. PostgreSQL can handle that order with suitable hardware, indexes, vacuuming, and query discipline, but this is an assumption—not a measured result. Initial consultation partitioning is deferred because PostgreSQL global uniqueness limitations would complicate the slot invariant. Milestone 8 must load-test representative volumes and consider archival or partitioning, especially for `audit_logs` and old consultations, before production scale is claimed.

## Retention and recovery assumptions

- Consultations, prescriptions, and payments: retain at least seven years as a planning assumption, subject to applicable healthcare/financial law.
- Audit logs: seven years; consider time partitioning and immutable archive after measured growth.
- Cancelled/past availability without clinical history: eligible for archival after one year.
- Sessions: remove 30 days after expiry/revocation; compromised-family evidence may be retained 90 days.
- Idempotency records: default expiry 24 hours; payment operations may choose a longer policy.
- Processed outbox events: retain 30 days; resolved dead letters 90 days.

Supabase backups, point-in-time recovery availability, retention configuration, and restore testing are deployment concerns. Milestone 8 must document RPO/RTO and demonstrate a restore; this milestone does not claim backup or load-test results.
